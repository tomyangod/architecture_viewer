## 战略命题

**在团队已有审查工具（CI / CodeRabbit / dependency-cruiser）之外，AV 以更低接入成本多解决一个值得持续付费的结构验收问题。**

"需求真实"（Stack Overflow 46% 不信任、DORA 验证成本转移）不等于"独立付费机会成立"。本计划用最低成本验证后者。

## 验证设计

### 招募

| 项 | 要求 |
|---|---|
| 团队数 | 5 个**非关联**团队（非作者自有仓、非作者直接同事） |
| 节奏 | 先让其中 2 个真正接入，不追求一次铺开安装量 |
| 代码库 | 真实、持续变更的代码库（非 sandbox、非 demo、非一次性 fork） |
| 技术栈 | 先聚焦 1–2 个熟悉栈（Python / JS-TS），避免验证变成多语言适配开发 |
| 团队画像 | 已有 PR 评审流程；常让 AI 一次改多个模块；有技术负责人愿意判断告警价值 |
| 使用版本 | 固定 `arch-viewer@0.12.2-rc.6`（npm `next`）；不混用工作区或 `latest`（仍为 0.12.1） |

**对照组按现状分两组记录，不混合宣传：**

| 组别 | 对照对象 |
|---|---|
| A：已有工具 | 与客户实际在用的 CI 检查 / CodeRabbit / dependency-cruiser 对照 |
| B：无自动工具 | 与现有人工评审对照 |

邀请话术直接对应任务：
> 在你们一个持续开发的仓库上，试用增量结构评论，比较它是否发现了现有流程遗漏的问题，以及是否增加评审负担。

首次接入可协助；后续观察使用是否**主动发生**。被作者反复催促才执行的使用不计入留存。

### 记录指标

| 指标 | 严格定义 | 目标 |
|---|---|---|
| 有效发现 | AV 报出、客户确认"有价值且现有工具没报"的 finding 数 | ≥1 / 团队 |
| 告警分类 | 每条客户反馈 finding 归入下方四分类之一 | 分类齐全 |
| 误报率（狭义） | 仅"事实错误"类占已评估 finding 的比例，同时报告评估覆盖率 | ≤20% |
| 漏报抽检 | 按 N/M/K 口径记录（见下），不得写"漏报率为零" | 护栏 |
| 净节约评审时间 | 客户自报 + 抽样核实 | 正值 |
| 首次付款 | 非关联团队因托管价值首次为 Pro 付费；关系性/支持性付款单列，不计入核心阶段门 | 第 8 周 ≥3 |
| 续费 | 首个计费周期后再次付费的团队数，与首次付款**分开统计** | 第 8 周后跟踪 |
| 支持工时 | 每个付费客户从接入起消耗的人工支持时长，按周记录 | ¥29 订阅需有正毛利 |

**告警四分类（客户说"不用管"不等于误报）：**

1. **事实正确且有行动价值**：促成修复、补测或有依据的评审决定；另标注是否为现有工具未报告的增量价值；
2. **事实错误**：依赖关系或违规判断不成立 → 修解析器/规则；
3. **事实正确但预期如此**：如共享枢纽模块扩大影响面 → 修呈现/接受机制；
4. **重复、无行动价值**：同一问题被拆成多条 → 修报告聚合。

每条经客户确认的 finding 归入一个主类别；未评估项记为"待确认"，不充当正确样本。误报率的分母为已评估 finding 数，并同时记录全部 finding 数和评估覆盖率。

**漏报抽检口径：**

> 本次抽检 N 个变更，其中 M 个属于产品承诺范围的结构问题，AV 漏检 K 个。

10 条抽检未发现漏检，只能表述为"该小样本未发现漏检"，不得表述为"漏报率为零/可靠性 100%"。

**付款纪律：** 低价支持作者、关系性付款要单独标注，不能直接解释为产品价值成立；若某客户需要大量人工服务才能用起来，该证据指向"服务需求"而非订阅模型成立。

### v18 复检记录（2026-09-11）

- v18 中 `BmccMediaSpider-main/` 本就在 `.gitignore`（第 22 行）但未被 git 跟踪；复检前 drift 清单路径不读 `.gitignore`，这是首日噪音根因。
- 修复后两条扫描路径（图提取、drift 清单）排除语义对齐：`.gitignore` 简单目录名、`.arch-viewer-ignore`、`externalDirs` 均生效。
- v18 复检（在沙箱可写的本地克隆上执行，场景等价：HEAD 无 AV 忽略文件、工作区有）：19 个自有模块全部保留，BmccMediaSpider 模块为 0，0 findings，绿灯 exit 0。
- 边界回归（自动化）：无斜杠目录名在任意层级跳过；有斜杠前缀只跳指定路径、不误伤同名目录；仅改排除配置时 verdict/PR 评论/HTML 均提示"分析范围变化，非代码删除"；旧基线无 scope 戳时不产生误报。
- 遗留观察项（不阻塞发布）：`broad-impact` 类高信号告警在试点中的重复率与阅读负担，按周记录，不在验证期重写风险引擎。

## 护栏

- 漏报（假绿灯）零容忍抽检——一次漏报导致事故可能摧毁留存；但抽检结论必须用 N/M/K 表述。
- 不得宣传为安全/业务正确性保证。
- 验证期每周投入 ≤20h 的既有护栏保留。
- 咨询收入不计入产品验证成功（可单独记录，但不改变 go/pivot 判断）。
- 允许插入的工程任务只有两类：阻碍客户接入，或影响报告可信度。

## 不做

在首批真实试点结果出来前，继续暂停：W21/W22 扩张项、新增语言与图种、多仓组织看板、SSO、插件生态、复杂 Team 自动计费、大范围风险评分改动。

不把 v18 自有仓数据、模拟体验评分、沙箱订单写入验证证据。A/B 两组对照数据分开记录，不混合成竞争优势宣传。不在验证期改 Apache 许可。不启动私有化交付能力建设（有书面合同再建）。
