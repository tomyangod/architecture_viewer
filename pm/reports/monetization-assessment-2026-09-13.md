## 二、难盈利 / 难获客的根因（按可改变性排序）

### 根因 1：Pro 的付费理由太薄（产品侧，可改变）

- 免费侧已提供自托管 Action 模板；Pro 唯一主付费点"托管 PR 评论"购买的是"省一次 CI 配置"，对个人开发者不构成 ¥29/月的理由。
- 2026-09-11 评估已发现付费交付与卖点错位（`web/lib/pro/host-drift.js` 跑旧图文漂移）；W24-01 修复后，Pro 交付才与卖点对齐——**这说明付费点本身也需要重新设计，不只是修 bug**。
- 第二付费点"本机文件夹看守 + 飞书/企微告警"更接近个人便利功能，非组织刚需。

### 根因 2：市场结构对当前定价模型不利（市场侧，部分可改变）

- **个人订阅（¥29/月）在中国开发者市场近乎不可行**：付费习惯、支付摩擦（爱发电/微信无订阅心智）、以及 depcruise 类免费替代并存。行业经验：中文开发者对订阅制 CLI 工具的付费转化通常远低于 0.5%。
- **愿意付费的是组织**，但组织采购要求发票、合同、对接——对应的是 ¥4,999+ 的 Team 入门包与人工销售，不是自助下单。这条路径慢，但与本品类真实预算（AI 编码工具预算线、质量问责需求）匹配。
- 海外（英文市场）付费意愿高一个量级，但获客竞争最激烈（CodeRabbit/Zügel 已占位），且当前无英文运营渠道与社区账号资产。

### 根因 3：获客只有脉冲，没有基线（渠道侧，可改变）

- 两次下载脉冲分别对应发布日与 09-10/11（新版本 + 掘金文），脉冲过后日下载归零 → **内容曝光能带来尝鲜，产品内没有留存/自传播抓手**。
- 遥测默认关闭 + 无安装后引导 → 漏斗从第一步就不可见，"安装→激活→留存"全靠猜。
- 触达名单 15 条且 12 条未发。按个性化私信 10–20% 回复率估算，约到 5 个团队访谈需要 **50–100 次有效触达**——当前名单量差一个数量级。

### 根因 4：solo + ≤20h/周 与"销售冲刺型验证"的资源矛盾（资源侧，需直面）

6–8 周付费验证本质是销售项目：触达、访谈、接入陪跑、支持、复盘。每周 20h 若仍以编码为主，验证必然失败。这不是战略问题，是时间分配问题。

## 四、建议清单

### A. 获客（本周启动，不等 Pro 完美）

1. **把 12 条"待发"全部发出**（掘金 B 模板 6 条、GitHub A 模板 3 条、Reddit 需先养号）。这是零成本、最高优先级动作。
2. **渠道扩容至 50+ 触达**：V2EX（/go/create、/go/programmer）、知乎（AI 编码质量话题）、X/Twitter（英文骨架已有）、Show HN（英文 README 已备）、r/ChatGPTCoding、Cursor 官方论坛。
3. **MCP 目录收录**：`av_guard` MCP server 提交到 MCP 官方 registry / 各大 MCP 聚合目录（mcp.so、Glama、PulseMCP 等）。这是本品类当前最精准的自然流量入口，且完全免费。
4. **把"图"变成传播载体**：六视图生成图默认带产品水印 + 落地页链接（开源协议允许、社区版保留），让用户晒图即拉新；去水印 + 托管分享页作为低摩擦付费点。图是获客手段、风险结论是产品本体——与战略修订结论一致，但需落实到产品行为。
5. **打开漏斗可见性**：安装后一次性提示"顺手 star / 提 issue / 反馈"；或提供 opt-in 匿名遥测。没有激活数据，8 周后的复盘仍然只能看下载量。

### B. 盈利模型（结构性修正）

6. **Pro（¥29/月）降级为"赞助 + 托管便利"档**，不再作为主验证对象；可实验年付 ¥199 或一次性买断。
7. **主推路径：4 周免费试点 → Team 入门包 ¥4,999/年**（托管评论 + 发票 + 支持工时承诺）。目标画像收窄为："已强制推行 AI 编码、技术负责人需要为架构质量问责的 20–200 人技术团队"。这条路径慢，但它与"谁真的会为这个品类掏钱"一致。
8. **试点期间把支持工时当产品指标记录**（pilot-validation-6w 已定义）——若某团队需要大量人工才用得起来，证据指向服务需求而非订阅，届时选项 C 的转向依据就齐全了。
9. **不建 SSO/多仓/私有化能力**（遵守既有放弃清单），有书面合同再动。

### C. 执行纪律

10. **每周 20h 分配建议**：触达与访谈 6h、试点接入与支持 6h、仅做"阻碍接入/影响可信度"的工程 4h、指标复盘 4h。验证期内编码不是杠杆，销售才是。
11. **新增先行指标：周有效触达数、回复数、访谈数**（写入 pm/metrics.md 周度表），不等 10-09 才发现招募失败。
12. **严守阶段门**：10-09 <3 留存 → 收缩修噪音；11-06 <3 付费 → 执行选项 C（服务化），产品转低成本维护。不延期、不用"再补几个功能"解释失败。

## 五、三个必须诚实回答的问题

1. 如果 depcruise + 一个 GitHub Action 已覆盖客户 80% 的需求，剩下 20% 的差异值 ¥29/月，还是值 ¥4,999/年的组织合同？——答案决定卖个人还是卖团队。
2. 第一批付费者更可能是"为省事的个人"还是"为问责的团队长"？现在没有任何证据支持前者；战略与资源应向证据可能出现的方向倾斜。
3. 如果 8 周后的结论是"产品价值成立但没人知道"，是否愿意长期把 50% 以上时间投入在销售与内容上？如果不愿意，选项 C（内部工具 + 服务化）不是失败预案，而是更诚实的终局。
