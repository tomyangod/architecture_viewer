## 10. fileCatches 按函数收紧（2026-09-12）

观察 §9 的 `web/server.js` FN：同文件任意 `catch {}` 即视为整文件已捕获。

| 改动 | 说明 |
|---|---|
| `catchSites[].owner` | 最近 enclosing function/method 名；模块顶层为 `null` |
| `nodeCatches(file, pathNode, ex)` | 只认：模块级 catch，或 `owner === pathNode.name`（class 节点还可认其 methods） |
| file entrypoint | 忽略函数内 catch-all，不再整文件吞 |

回归：`test/exception-drift.test.js` 新增「无关 catch-all 不压 R19」+「入口函数自身 catch 仍 TN」。

## 11. Python call 边：sys.path 根 suffix（2026-09-12）

POM FN 根因不是动态调用，而是运行时 `sys.path` 插入 `backend/`：

`from services.alerts_service import alerts_detail` 被解析成 `ext:services`，`handle_alerts_detail` → unresolved-call，R19 走不到 controller。

| 改动 | 说明 |
|---|---|
| `uniquePyModuleSuffix` | 仅 ≥2 段路径；仓内独一 `*/services/alerts_service` 才绑定 |
| 单段 specifier | 不 suffix（避免 `from json import dumps` 绑到 stray `json.py`） |
| 歧义 | 两处 `services/x` 保持 unresolved |
| alias | `from x import foo as bar` 的 call 用 imported 名 `foo` 找实体 |

先复验 call 边（只读）：`handle_alerts_detail → alerts_service#alerts_detail` high。产品仓真实 throw 标 TP 见 **§12.1**。W21-01b / 取消 reportOnly 仍暂缓。

## 13. catch 再收紧：loadGuard + 词法包围 throw（2026-09-12）

针对 §12.2 仍 FN：

| 改动 | 说明 |
|---|---|
| `catchSites[].loadGuard` | 模块顶层 try 体像 `require` / `import` / `readFileSync(...package.json)` 且行数少 → 标 loadGuard |
| file / 函数路径 | **忽略** loadGuard（require 兜底不再挡业务异常） |
| `catchSites[].tryStart/tryEnd` | try 语句行范围 |
| `impl.throwSites[{name,line}]` | throw/raise 带行号 |
| `originCatches` | 原点：catch-all 必须**词法包围**该异常的 throw 行；无行号时忽略 catch-all，只认 typed catch |

回归：`test/exception-drift.test.js` 新增 3 条（loadGuard file 入口 / 原点无关 catch-all / 词法包围 TN）；R19 **11/11 pass**。

真实仓抽查：`web/server.js` L25/L40 已为 `loadGuard:true`；`scan` 自身 catch 在 L327–332，不包围函数其它位置的 throw。W21-01b / 取消 reportOnly 仍暂缓；产品仓再造一次 `scan→web/server` → **TP（§14）**。
