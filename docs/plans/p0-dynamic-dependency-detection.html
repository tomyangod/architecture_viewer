1. 背景与目标

Architecture Viewer 的核心定位是架构关系增量检测器。字面量动态导入已经做完（import()、importlib.import_module()、dynamic: true、变量路径记 unresolved-dynamic-import）。本设计不把 AV 扩成代码质量总验收，只补静态写在装饰器里、但当前不成架构边的装配关系。

  • P0：NestJS @Module 装配——imports / controllers / providers 里的类名往往已有文件 import 边；缺的是「这个模块把谁装进来了」。只改装饰器数组、不改 import 时，增量报告会漏。
  • 不是盲区：TS 构造注入——constructor(private svc: FooService) 已走 method-param。不要再为 @Injectable() 重做一遍。
  • 不是盲区：@Controller('users')——参数是路由前缀字符串，不是类型引用。
  • P1：Java 类型边——字段/构造参数已抽到 members，但 extract-graph.js 对 Java 只落 extends/implements。补边后 Spring 注入大多会自动出现，不必先做注解引擎。
  • 可选：动态边画虚线——数据已在边上，渲染层未消费。这是可读性，不是漏报。
  • 不做：配置驱动 / 插件入口 / 跨文件变量——CHANGELOG 已划界；静态分析到此为止。

目标：不扩展产品边界，补图谱盲区。条件写反、慢 SQL、安全漏洞、登录态、UI/日志文案不进本设计。

3. 三个真实缺口

Gap 1：模块装配边缺失（不是「完全看不见 DI」）高

问题：@Module({ imports: [FooModule] }) 通常伴随着 import { FooModule } from '…'。文件级 import 边已在。缺的是实体级装配边：AppModule → FooModule（role=import）。只改数组、不改 import 时，当前 delta 为空。

不要做成：通用 DI 容器模拟、@Inject('TOKEN') 字符串令牌、TypeOrmModule.forRoot() 运行时配置、新 finding di-dependency-removed（边增删已在增量里）。

典型场景：

import { FooModule } from './foo/foo.module';  // 已有 import 边
import { AppController } from './app.controller';
import { AppService } from './app.service';

@Module({
  imports: [FooModule],          // ← 缺：AppModule -di-registered→ FooModule
  controllers: [AppController],  // ← 缺：装配边（import 边已在）
  providers: [AppService],
})
export class AppModule {}

// 已覆盖，不要重复做：
constructor(private svc: FooService) {}  // method-param

// P1 再做：Java members 已有 type，但没落 field-type / method-param
@Autowired
private PaymentGateway gateway;

Gap 2：动态边渲染无差异 中

问题：dynamic: true 字段已存在于边对象中，但 lib/layers.js 的 renderLayeredFlowchart() 和 lib/generate.js 的 C4 生成器都不消费此字段。所有边统一渲染为实线 -->。

影响：用户看到 A --> B 时无法区分"静态 import（编译期固定）"还是"动态 import（运行时按需加载）"。这在评估变更影响面时会造成误判——动态依赖的断裂风险与静态依赖不同。

注意：generate.js 第 366/374 行已使用 -.->（虚线）渲染"进入运行时"边，说明渲染层已支持虚线语法，只是未应用到 dynamic 标志上。

Gap 3：变量动态导入无启发式解析 低

问题：import(variableName) 当前一律指向 dyn:unresolved 虚拟节点。对于简单常量赋值模式（const mod = './foo'; import(mod)），AV 可以通过 AST 变量追踪解析目标，但当前未实现。

影响：实际项目中变量驱动动态导入占比不高（大多数 import() 用静态字符串路径），但缺失会让图谱出现"黑洞节点"，影响可读性。

4. Gap 1 设计：DI 装饰器依赖提取

4.1 设计原则

  • 框架特定，不做通用 DI 容器模拟——只提取装饰器参数中引用的类/模块名，不做运行时注入行为推演
  • 复用已有 AST 基础设施——tree-sitter 已解析装饰器节点，只需增加遍历逻辑
  • 新增边类型 di-registered——与 import 边区分，便于风险规则差异化处理
  • 默认启用，不需要额外配置——装饰器检测是纯静态分析，无外部依赖

4.3 实现方案

在 lib/extract/jsts.js 中新增 extractDecoratorDependencies(ast, result, filePath) 函数：

// 伪代码 — 在 extractFile() 中，类型/函数提取之后调用
function extractDecoratorDependencies(ast, result) {
  // 1. 遍历所有 decorator 节点（TS: decorator / Java: annotation）
  const decorators = collectNodes(ast, 'decorator');

  for (const dec of decorators) {
    const name = getDecoratorName(dec);       // @Module → "Module"
    const arg = getDecoratorArgument(dec);     // ({ imports: [FooModule] })

    if (DI_PATTERNS.has(name)) {
      const pattern = DI_PATTERNS.get(name);

      // 2. 从装饰器参数中提取引用的类名
      const refs = pattern.extractRefs(arg);
      //    refs = ['FooModule', 'AppController', 'AppService']

      for (const ref of refs) {
        result.diDependencies.push({
          decorator: name,        // 'Module'
          refName: ref,           // 'FooModule'
          role: pattern.role,     // 'import' | 'provider' | 'controller'
          line: dec.startPosition.row + 1,
        });
      }
    }
  }
}

// 框架模式注册表
// 只认 @Module 的三个数组。不要扫 @Controller / @Injectable。
const MODULE_ARRAY_KEYS = ['imports', 'controllers', 'providers'];
// extractArrayElements(arg, key) → 标识符列表；role = key

在 lib/extract-graph.js 的图组装阶段，新增 di-registered 边创建逻辑：

// 在 extractGraph() 中，import 边处理之后
for (const fe of allFiles) {
  if (!fe.diDependencies) continue;
  for (const di of fe.diDependencies) {
    // 通过 name → entity 解析（复用现有 resolveEntityByName 逻辑）
    const targetEntity = resolveEntityByName(di.refName, fe.file);
    if (targetEntity) {
      addEdge({
        from: 'file:' + fe.file,    // 或 entity 级边
        to: targetEntity.id,
        type: 'di-registered',
        file: fe.file,
        line: di.line,
        decorator: di.decorator,    // 'Module' | 'Controller' | ...
        role: di.role,               // 'import' | 'controller' | ...
      });
    }
  }
}

5. Gap 2 设计：动态边差异化渲染

5.1 渲染规则

边类型Mermaid 语法视觉含义
静态 importA --> B实线，编译期固定依赖
动态 import (dynamic: true)A -.-> B虚线，运行时按需加载
DI 注册 (di-registered)A -.->|注册| B虚线 + 标签，框架容器管理
unresolved 动态A -.-> dyn:unresolved虚线 + 红色目标节点

5.2 实现方案

修改 lib/layers.js 的 renderLayeredFlowchart() 边输出逻辑：

// 当前代码（layers.js ~344行）：
edges.push(`  ${from} -->|${verb}| ${to}`);

// 修改后：
function edgeToMermaid(edge) {
  const arrow = edge.dynamic || edge.type === 'di-registered'
    ? '-.->'   // 虚线
    : '-->';   // 实线
  const label = edge.label ? `|${edge.label}|` : '';
  return `  ${edge.from} ${arrow}${label} ${edge.to}`;
}

同时修改 lib/generate.js 的 C4 图生成器，在边输出时检查 dynamic 字段。

5.3 Delta 图中的动态边

在 lib/diff-graph.js 的 Delta 视图中，新增/删除的动态边也用虚线表示。修改 edgeLabel() 函数：

function edgeStyle(edge) {
  if (edge.dynamic || edge.type === 'di-registered') return '-.->';
  return '-->';
}

6. Gap 3 设计：变量动态导入启发式解析

6.1 解析策略

对 import(variableName) 和 require(variableName)，按以下优先级尝试解析：

  1. 同文件 const 字面量——const mod = './foo'; import(mod) → ./foo，边带 resolvedFromVariable
  2. 其余一律不解析——let/var、跨文件、config.modulePath、环境变量、${} 插值：保持 unresolved-dynamic-import

6.2 实现范围

仅实现策略 1（同文件常量赋值），ROI 最高且最可控：

// 在 jsts.js 的 call_expression 遍历中（~688行后）
if (!spec) {
  // 尝试从同文件变量赋值中解析
  const varName = extractIdentifier(args);
  if (varName) {
    const constValue = findConstAssignment(ast, varName);
    if (constValue && typeof constValue === 'string') {
      spec = constValue;
      // 标记来源，便于风险规则区分
      result.imports.push({
        specifier: spec,
        line: call.startPosition.row + 1,
        isCjs: isRequire,
        dynamic: isImport,
        names: [],
        resolvedFromVariable: varName,  // 新标记
      });
      continue;
    }
  }
  // 仍然无法解析 → unresolved
  result.imports.push({
    specifier: null,
    line: call.startPosition.row + 1,
    isCjs: isRequire,
    dynamic: isImport,
    unresolved: true,
    names: []
  });
}

8. 风险评估

风险级别缓解措施
tree-sitter 装饰器解析不完整（TS decorator 语法曾有重大变更）中对 TS 5.x 装饰器语法做兼容性测试；decorator 节点解析失败时静默跳过，不中断提取
di-registered 边产生大量噪音（NestJS 项目模块多）中增量报告中默认折叠 DI 注册边（类似 declared-in 边的折叠策略），仅在 --all 时展开
变量追踪误解析（变量在运行时被修改）低仅追踪 const 赋值（不含 let/var），并在边中标记 resolvedFromVariable 以便人工核查
渲染虚线后图过于密集可读性下降低Delta 图中仅在"仅变更"和"仅违规" tab 中区分虚实线；全量视图保持实线
