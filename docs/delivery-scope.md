# 首发交付范围

本地版候选版本用于人工架构评审，不是无人复核的合并裁决器。首发范围：

- **本轮结构变更报告**：CLI `session start / report / guard` 与 MCP `av_session_start`、`av_session_report`、`av_guard`；全仓摸底用 `av_check_layering`。
- **可定位源码的局部依赖图 / 结构总览**：`arch-viewer generate` 默认写 `block-diagram.md`（静态模块分层，不是运行时真相）。类图仅按需、围绕本次修改的类和邻居。编排流水线页脚宣称的校验仅限路径存在性、Mermaid 语法与层归属；节点语义（框架标注、业务名）未经运行时核查，需人工复核。
- **人工确认后的 Archify 讲解图**：`archify-export --confirm` / MCP `av_archify_export` 且 `confirm=true`。内置 HTML（Before/Delta/After）始终可用，无需安装 Archify。
- 六视图生成器仍可通过 `--compat-six-views` 或 `--views` 调用，属于兼容功能，**停止扩张**，不作为首发卖点或质量承诺。
- **未选中的用户图保留**：默认 generate 仅删除与当前随包模板逐字节一致的未选中图；修改过、来源不明的旧模板或符号链接保留，不凭「职责描述」等正文词语判断所有权。本轮选定与「磁盘保留未更新」写入 `.generate-receipt.json`，CLI 与 HTML 会标识，避免把旧图当成本轮新产物。选中视图仍按原行为重新生成并覆盖，不承诺所有图无损合并。

同一仓库、同一基线、同一规则文件时，CLI 与 MCP 的核心结论应一致。
`av_guard` 自 0.12.0 起已存在；旧版本的工具清单不能作为当前版本的依据。

## 结果含义

- `analysis.status=ok` 表示选定扫描范围内未发现已知的完整性故障，不代表所有运行时依赖都已识别。
- `analysis.allowGreen=true` 只允许按已识别风险给出结论，不保证代码正确、没有漏报或可以直接合并。
- 分析失败或不完整时：退出码 **3**，JSON/HTML 带 `analysis.status` / `analysis.allowGreen` / `analysis.reasons`。这不是「没有违规」，脚本不得当成成功。
- 正常分析的风险门：退出码 **0** 表示低于配置的阻断阈值，**1** 表示达到阈值；参数/配置错误为 **2**，基线不存在或失效为 **4**。
- 自动分层是建议；覆盖率不是准确率。目录名（如 `tools/monitoring`）不能证明可执行入口。仅由未确认分层推断出的跨层问题应作审查提示，不触发跨层阻断；先确认两端分层配置与依赖证据，再判断是否需要改代码。该策略不取消其他有独立证据的风险规则。
- 测试关联是静态证据，不是执行结果。未识别到关联测试或关联测试文件没有变化，不能推出「没有测试跟进」；测试文件改动也不证明测试通过或覆盖了本轮行为。
- 六视图的结构校验不证明图中关系真实。影响面是已提取依赖图上的分析，不是完整的运行时调用追踪。

## 会话解释与升级

`av_explain_finding(from=session)` 解释的是已保存报告的 finding 和节点/边证据，不再强制要求快照基线文件。Git HEAD 基线与显式 snapshot 均支持；CLI 生成的会话报告也可由 MCP 解释。

返回的 `evidence.generatedAt`、`baselineKind`、`gitHead` 与基线/当前结构指纹标明报告对照点。后续修改源码、移动 HEAD 或刷新 HEAD 缓存不会把新事实混入旧报告。它不是实时验收；修改后须重新 `av_guard` / `av_session_report`。过期存根、缺少解释证据的旧报告或损坏报告会显式拒绝，要求重生成报告，**无需为了解释而接受当前结构或刷新快照基线**。

源码、SQL/Prisma 和测试内容哈希仅规范化 CRLF → LF，不忽略其他空白或真实编辑。Git HEAD 的旧哈希缓存自动重建；无法比较的旧显式快照标记 `summary.sourceComparison=incompatible-hash-version`、`sourceChanged=null`，不是「源码未变」。保留旧快照，在人工确认的版本上重建后再做可靠的内容级增量归因；不要为了消除升级差异直接接受当前未审查改动。

## 六视图与精修的证据口径

六视图不再是默认交付。`Validation: PASS` 只表示**已写出视图**的图协议与库存覆盖检查通过，不是架构准确性证明。`drift` 是扫描库存与图的覆盖差异，不是运行时错误；有意省略的辅助目录需由人确认。

骨架图是静态源码库存草稿：只展示有来源的节点和关系。未找到关系时允许保留未连线节点，不用「协作」或 `uses` 把目录和类按顺序串起来。导入关系不能读作运行时调用，图中没有边也不能证明运行时不可达。C4 Container/Component 中的源码模块不能称为进程或容器。

生成缓存核对源码内容、分层/排除配置、生成器身份、引擎和**所选视图**的实际内容。占位稿覆盖输出、改配置、切换引擎或升级实现都会使旧缓存失效。部分 `--only` 精修不能代表全部视图完成；源码变化后，骨架外观不变也不能证明精修无需重跑。

精修提示不再预置某个示例业务、Web 框架或数据库。但提示改进和离线模拟测试不保证模型遵循，也不等于真实模型输出通过人工复核。AI 精修仍不在首发准确性承诺内，也不再对「一键精修六图」做质量承诺。

专用 Archify 导出入口 `archify-export --confirm` / `av_archify_export(confirm=true)` 需要人工确认。另一路 `session report --renderer archify|auto` 是调用方显式选择报告渲染器：允许尝试本机 Archify，并按回执标明实际渲染器与降级原因；它不使用专用导出的 `confirm` 参数。默认 `builtin` 不触发这条路径。两种显式选择都不代表关系已被程序证明；Typed JSON、Schema 校验和路径存在，都不能单独证明一条关系正确。

## 扫描与解析边界

- 默认排除依赖、构建产物、隐藏目录及部分开发资产；扫描白名单还会进一步收窄范围。
- 根 `.gitignore` 的字面目录规则保留根锚定和顺序：`/runtime/` 不排除 `tools/runtime/`，`runtime/` 可在任意深度匹配。
- 不承诺完整 Git ignore 语义：嵌套 `.gitignore`、通配符和转义规则尚不完整支持。无法支持的规则采用保守扫描策略，可能多扫，不能把扫描结果等同于 `git ls-files`。
- 反射、动态导入、运行时修改模块路径、星号导出和复杂再导出不保证可解析。未解析引用不能当成已确认的第三方包，也不能凭同名类推断本地依赖。
- `av_check_layering` 返回 `mode=snapshot`，不把当前依赖、体量和孤立实体称为本轮新增。它们放在 `inventory`，分层违规另计 `layerViolationCount`；日常使用会话入口，真正新增的依赖仍会提示。
- MCP 扫描返回 `runtime.packageVersion`、`packageRoot`、`analyzerSourceDigest` 和 `scannedAt`，用于区分实际运行包与旧报告。摘要是包内分析源码的身份，不是准确率或完整性背书。

**不在首发质量承诺内：**

- AI 精修 / LLM / orchestration 模式
- VS Code / Cursor 扩展分析路径（不加载团队规则、未接完整性门）
- 多仓 / workspace 聚合报告
- 账号、支付、托管 SaaS
- 无人复核的自动阻断合并

## 离线与安装

会话分析和内置报告不需要 LLM Key。默认 `generate` 只写结构总览，使用本地引擎，不因环境中存在 Key 而选择精修。`--compat-six-views` 才写齐兼容六图。
首次 npm 安装需要取得依赖包；「离线分析」不等于「无缓存、无网络也能首次安装」。
仓库中的 `node scripts/verify-packed-delivery.js` 默认使用独立空缓存验证安装包。受限网络下可显式使用 `--offline --npm-cache /绝对路径/已预热缓存`；仍会创建全新安装目录并执行原生解析与 CLI/MCP 验收，结果会记录缓存模式。缓存验收不能代替首次联网下载验证。

## 平台与版本验收

`engines.node >=18` 是安装声明，不是全部组合均已验证的证明。CI 矩阵只是待执行的验收配置，必须查看该发布提交对应的实际结果。

候选包发布前应保存：干净提交 SHA、包版本、tarball SHA-256、操作系统/架构/Node 版本、测试及安装包闭环结果、已知局限。
此前独立加固提交 `64dcdc4` 与已发布 RC2 的发布提交 `85a9f6a` 来自不同分支；发布 RC2 并未包含该加固提交。`0.12.2-rc.3`（源提交 `81e6c43`）、`0.12.2-rc.4`（默认交付收缩）、`0.12.2-rc.5`（解释闭环与分层门禁解耦）与 `0.12.2-rc.6`（出图措辞如实化与环/影响面结构化解释，源提交 `8863ed6`）先后发布到 npm 标签 `next`；`latest` 仍为 `0.12.1`。接入须钉已发布版本或 `@next`，不能复用 `0.12.2-rc.2` 身份，也不能将未提交改动当作已发布产物出售。
尚未实跑的平台不得标为通过；升级/重建基线前应保留客户原快照，不承诺未知未来格式兼容。
解析器修复可能改变同一份源码的图边。升级后先备份旧基线，在人工确认的代码版本上重建基线，再开始新会话；跨解析器版本的图差异不能直接归因于本轮代码变更。
同时复核已有分层配置：显式 `.av/layers.json` 会继续生效，旧版自动建议若被保存为配置（例如把整个调度目录归为 util），不会因升级自动变正确。真实依赖边命中错误的分层配置仍可能产生误报；不能把新版本的红灯数量直接称为真阳性数。
